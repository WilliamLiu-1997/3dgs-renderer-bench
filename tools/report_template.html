Where sorting runs

Worker sorting runs asynchronously; GPU sorting is ordered within the GPU command stream. Async completion includes preparation, transfers, sorting and handing back the result. A separate diagnostic measures the first-to-last radix pass span. Each run alternates between two camera directions, with 4 warm-up iterations and 16 measured samples.

The GSL WebGPU diagnostic separates projection and radix; main frame measurements retain the original combined path. PlayCanvas keeps native pass boundaries. Its CPU async metric measures Worker request to result delivery; GPU radix excludes projection and compaction. These measure renderer pipelines with different active counts and key encodings, not equal-input sorting algorithms. SuperSplat keeps its native projection/radix boundaries; its GPU sort span excludes projection.

Sorting precision, explained

All sorted tests use camera-axis depth. Source encoding, depth-key precision and sort latency are separate properties. A wider key preserves more depth distinctions, while an asynchronous result may still lag behind the current camera.

PlayCanvas derives its depth range from active scene bounds, rather than directly from camera near/far. Its CPU bin weighting and GPU key encoding differ. Key widths alone do not establish image equivalence.

Nearly coincident splats can share a quantized key and change alpha blending. Sorting uses Gaussian center depth and does not provide per-pixel ordering for intersecting Gaussians. GSL uses its default 24-bit sorting throughout this report. Spark uses extended source and accumulator encoding in timing and image tests.

Memory

Sum JS heap, ArrayBuffer/external backing storage and WASM capacity within each post-GC snapshot, including the main thread and live Workers. Take the maximum across sorted cases per run, then the median across three runs. GPU allocation is aggregated separately. Stochastic render targets are excluded. MiB = 2²⁰ bytes.

JS heap + ArrayBuffer + WASM · MiB

Explicit GPU allocation · MiB

The combined value is the sum of the recorded memory categories. ArrayBuffer includes CDP external-string backing storage; WASM uses live Worker linear-memory capacity. It is an accounting sum, not process RSS or deduplicated physical memory. Raw component measurements remain in harness/results.

Explicit GPU allocation tracks buffer, texture and renderbuffer capacity, excluding measurement-query buffers, driver overhead, alignment and the swapchain. It is allocated resource capacity, not physical VRAM usage; Apple uses unified memory. Browser process-tree RSS includes unrelated browser/GPU-process memory and can double-count shared pages, so it is retained only as raw diagnostics, not used for the memory comparison.

Measurement scope

Full inputs, fixed resolutionElevator: 2,796,503 splats; HotelFareza: 12,202,010. Canvas dimensions follow the built-in screen’s logical size and default DPR. Headless Chrome uses the real Metal GPU without display-rate throttling. FOV 45°, near 0.1, far 3000, background #101418. Matching world-space cameras; native frustum, opacity and size culling remain active.

Spark source precisionBoth source and accumulator use extended encoding, with runtime assertions. Base records are 32 bytes with float32 positions; “extended” does not mean every field is float32. Neither uses PackedSplats. SH3 is retained. The 32-byte source record and the 32-bit sort key describe different things.

Gaussian Splat Lite source and accumulatorGaussian Splat Lite 1.1.5 uses 32-byte base records: float32 positions; float16 RGB, alpha and log-scale; a 10/10-bit octahedral rotation axis plus a 12-bit angle. SH3 remains enabled; each RGB coefficient uses 32 bits (8-bit channel magnitudes, 3 sign bits and a shared 5-bit exponent). WebGL2 uses highp shader arithmetic and a 32-byte accumulator with the same attribute layout.

Gaussian Splat Lite WebGPU precisionNative WebGPU computes projection in float32 and stores 32-byte projected records: screen centers use 16-bit signed normalized values; axes, axis ratio and RGB use float16; view depth, alpha, support radius and kernel power use float32. The report uses default 24-bit depth sorting.

PlayCanvas Engine and rendering settingsPlayCanvas 2.23.0-beta.20 on WebGL2 and WebGPU uses large (32-byte work buffer), minPixelSize 2, minContribution 0, alphaClipForward 1/255, antiAlias false and camera-axis sorting. Spark uses radius 2–512, pre-blur 0.3, compensated blur 0, focal adjustment 2 and clipXY 1.25. GSL uses radius 1–256 with the same blur, focal, clip and alpha values. Native projection and sorting differences remain.

SuperSplat rendering pathSuperSplat 3.4.2 uses its own WebGPU projector and rasterizer on PlayCanvas 2.23.0-beta.20. Full PLY/SH3, matching cameras, background and resolution; minPixelSize 2, native covariance pre-blur 0.3. Native stochastic depth occlusion uses its default enabled setting; motion-adaptive contribution culling is disabled. Raw stochastic uses native 1-sample coverage; resolve adds the native 2×2-quad spatial filter, with warp and temporal accumulation off. Native radius limits, alpha handling, source encoding and projection remain different.

Caching and motionStatic tests still draw every frame and retain internal projection caches. Moving tests use matching ±45° sinusoidal camera sequences; asynchronous backends may draw with a previous ordering. Frame time therefore does not include waiting for the newest sort. Motion advances per frame, so results do not claim equal-time interactive FPS.

Supported featuresRendering settings across six backends are adjusted as closely as possible; GSL uses default sorting only. Raw stochastic cases compare PlayCanvas WebGPU, SuperSplat WebGPU and both GSL backends. SuperSplat and GSL also measure native spatial resolve. Static and moving views are tested with temporal accumulation off. Spark and PlayCanvas WebGL2 have no stochastic case in this protocol.
