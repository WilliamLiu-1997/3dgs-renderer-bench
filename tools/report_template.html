Where sorting runs

Worker sorting runs asynchronously; GPU sorting is ordered within the GPU command stream. Async completion includes preparation, transfers, sorting and handing back the result. A separate diagnostic measures the first-to-last radix pass span. Each run alternates between two camera directions, with 4 warm-up iterations and 16 measured samples.

GSL separates projection and radix only for this diagnostic. Engine, Viewer and Radix GPU use native pass boundaries. Radix CPU waits for one complete sort per sample: GPU key projection/readback plus Worker sorting and result delivery. Worker execution and message round trip are shown separately. Frame tests retain asynchronous sorting. Native pipelines and active counts differ; these are not equal-input sorting algorithms.

Sorting precision, explained

All depth-sorted groups use radial ordering. Source encoding, key precision and sort latency are separate properties. Engines may encode distance or squared distance, so equal key widths do not guarantee equal quantization. Asynchronous results may lag behind the camera.

PlayCanvas and Viewer map squared-distance float bits over a range starting at nearClip / 1024 and ending at the active scene bound. CPU radial sorting uses 16-bit counting keys; GPU sorting chooses 16–20 bits from the active count and rounds to the radix width. This Apple GPU uses portable 4-bit radix. Equal key widths do not establish image equivalence.

Nearly coincident splats can share a quantized key and change alpha blending. Sorting uses Gaussian center distance and does not provide per-pixel ordering for intersecting Gaussians. Ordinary depth-sorted GSL cases use its default 24-bit sorting. Spark uses extended source and accumulator encoding in timing and image tests. Raw stochastic GSL frames instead use the default 16-bit axial front-to-back ordering; PlayCanvas stochastic rendering skips sorting.

Memory

Sum JS heap, ArrayBuffer/external backing storage and WASM capacity within each post-GC snapshot, including the main thread and live Workers. Take the maximum across sorted cases per run, then the median across three runs. GPU allocation is aggregated separately. Stochastic render targets are excluded. MiB = 2²⁰ bytes.

JS heap + ArrayBuffer + WASM · MiB

Explicit GPU allocation · MiB

The combined value is the sum of the recorded memory categories. ArrayBuffer includes CDP external-string backing storage; WASM uses live Worker linear-memory capacity. It is an accounting sum, not process RSS or deduplicated physical memory. Raw component measurements remain in harness/results.

Explicit GPU allocation tracks buffer, texture and renderbuffer capacity, excluding measurement-query buffers, driver overhead, alignment and the swapchain. It is allocated resource capacity, not physical VRAM usage; Apple uses unified memory. Browser process-tree RSS includes unrelated browser/GPU-process memory and can double-count shared pages, so it is retained only as raw diagnostics, not used for the memory comparison.

Measurement scope

Full inputs, fixed resolutionElevator: 2,796,503 splats; HotelFareza: 12,202,010; WillaGlobalPoland: 14,469,103. Full PLY/SH3 inputs, fixed cameras, 3024 × 1964 physical pixels, vertical FOV 45°, near 0.1, far 3000, background #101418.

Spark source precisionBoth source and accumulator use extended encoding. Base records are 32 bytes with float32 positions; “extended” does not mean every field is float32. SH3 is retained. The 32-byte source record and the 32-bit sort key describe different things.

Gaussian Splat Lite source and accumulatorGSL uses its published source and accumulator encodings with full input SH. Effective rendering settings and the exact dependency versions are recorded per run.

Three.js versionsGSL and Spark use Three.js r187; Radix 0.0.1 uses r186 because its WebGPU path is incompatible with r187. Native sorting and caching remain enabled.

PlayCanvas Engine and rendering settingsEngine and Viewer use large work buffers, minPixelSize 2, minContribution 0, alphaClipForward 1/255, antiAlias false, colorUpdateAngle 0 and radial sorting. Spark and Radix use minimum radius 2 and maximum 512. GSL uses minimum radius 1 and exposes no maximum-radius setting. Native coverage and projection can still differ.

SuperSplat ViewerViewer is created through its public API with the pinned Engine peer. Sorted rendering, large work buffers, shared camera and resolution; post effects and performance scaling are off. Its model rotation is reset to match the original PLY. Its own update loop remains active while automatic draws are suppressed.

Caching and motionStatic tests still draw every frame and retain internal projection caches. Moving tests use matching ±45° sinusoidal camera sequences; asynchronous backends may draw with a previous ordering. Frame time therefore does not include waiting for the newest sort. Motion advances per frame, so results do not claim equal-time interactive FPS.

Supported featuresEight backends measure sorted rendering. PlayCanvas WebGPU and both GSL backends also measure raw stochastic rendering. Static and moving main/closer views use separate comparisons. No spatial resolve or temporal accumulation.
